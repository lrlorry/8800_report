\subsection{解释 OpenAI 比较}

两个 OpenAI 导出均来自 Qdrant 的 DBpedia 嵌入，因此可以用于比较维度差异 \cite{data_openai1536,data_openai3072}。解释维度变化前先检查了行对齐：截断并重新归一化后，全部 1,000 个查询行和 10,299 个抽样数据库行的余弦均为 $\geq0.9980$，中位数为 1.000000；真实近邻集合平均共享十个邻居中的 9.046 个。这些检查支持行对齐，但不构成原始实体 ID 的完整连接。维度翻倍后，对 CAGRA fp32 的比值仍为 1.747，对 RaBitQ 的比值从 1.130 变为 1.157，因此维度本身不能解释观察到的优势。

128 probes 下，较小的精排倍率伴随较大收益：OpenAI 为 4--8，Vogue 为 64，arXiv 为 100，而后续全池校准对 arXiv 选出 200。这是跨工作负载的相关关系，并非受控因果比较；\cref{sec:8-centring} 检验一种表示层面的解释。小幅差距和测量敏感性见 \cref{sec:7-8}。

\subsection{与 CPU 实现的历史比较}
\label{sec:7-cpu}

较早的一次比较使用 JHQ 作者的 CPU 实现，在相同召回率下得到 GPU／CPU 吞吐比：Vogue 为 52--85，arXiv 为 56--98，OpenAI-1536 为 85--108，OpenAI-3072 为 75--77。测试在同一服务器的 Xeon Platinum 8470Q 上进行，并对 CPU 工件做了本地兼容性和 Recall@10 修复。图中的 CPU 前沿对 Vogue 和 OpenAI-3072 取 16、32 线程较快值，另外两个数据集采用 32 线程。扫描范围为 $\alpha\in\{2,4,8,16,32,100\}$ 及 128--1,024 probes；更小 probe 数受线程启动开销影响而排除。比值在相同召回率处按吞吐对数插值得到。

这些是历史实现之间的比较。GPU 使用较早的实现，CPU 码本单独训练，两个 OpenAI 的 CPU 索引有 4,096 个列表，而 GPU 为 8,192 个。多数 CPU 配置只计时一次。较晚的十月 CPU 精排研究也未匹配设置：Vogue 使用 1,024 个列表和 $[8,4]$ 位，而主比较为 4,096 个列表。若要给本文评测 GPU 版本的硬件加速比，仍需匹配索引与计时条件。

\subsection{LUT 分解与吞吐}

两张 16 项表在 24 个配置中的 22 个是最快的已测形式，但实数算术中的分解不意味着 FP32 分数或最终 ID 完全相同。\Cref{fig:7-lut} 测试六个数据集、8、32、128、512 四种 probe 数，固定 $\alpha=100$，并令 $\glut\in\{1,2,4,8\}$。五轮采用 batch 1,000，Stella 为 999。两个例外接近持平：arXiv 在 128 probes 下，一组快 0.23\%；OpenAI-3072 在八个 probes 下，四组快 0.84\%。两组对一组的配对比较赢得 24 个配置中的 23 个，各数据集几何平均比为 1.021--1.318。

各配置的两组／一组比值为 $0.998$ 到 $1.914$。四组和八组每个子空间均存 16 项，却需要更多查表和加法，较小的表并非总能补偿这些成本。占用率和指令成本未被单独分离。每个四变体配置内，最大报告召回差为 $10^{-4}$。

严格分数检查在 Vogue、arXiv 和 OpenAI-3072 上，固定 128 probes、$\alpha=100$ 比较相同候选。整表与 $16+16$ 表有 22.6--26.1\% 的分数 bit 模式不同，最大相对误差为 $4.53\times10^{-7}$。全部表形式之间，20.5--29.4\% 不同，最大误差为 $4.63\times10^{-7}$。Vogue 的 256 条查询中有二至四条最终 ID 不同，arXiv 和 OpenAI 未出现差异。即使短名单不变，最终 ID 仍可变化，因为舍入后的主码分数会进入精排（\cref{sec:a-t4-t5}）。

\subsection{打包访问与协作残差评分}

按字打包访问在六个数据集、四种 probe 数和 $\glut\in\{1,2\}$ 的 48 对匹配比较中，提升吞吐 $1.012$--$1.658\times$，召回差最多为 $10^{-4}$。两种布局均以子空间为主序；改动结合了按字读取与解包（\cref{fig:7-packing-refinement}）。

精排对照分离了宽载入与协作。L0 是标量参考，L1 只改变载入路径，L16 为每个候选分配 16 lanes。同一轮中轮换变体顺序，共五轮，每轮每变体搜索三次。十二个普通配置的 L16 端到端提升为 $1.015$--$1.789\times$；独立的高预算 arXiv 对照在 $\alpha=200$ 达到 $2.383\times$（\cref{tab:7-refinement}）。

简单的阶段占比模型能接近预测端到端收益。仅改变载入的 L1 保持 L0 的 bits，在 arXiv 上获得 $1.368\times$。采用 lane 协作、$\alpha=100$ 时，arXiv 精排从 4,277.5 降至 716.8\,$\mu$s，内核提升 $5.97\times$，整体却为 $1.789\times$。OpenAI-3072 的内核提升为 $8.81\times$，整体为 $1.171\times$。对于基线 wall 时间占比 $f$ 和精排加速比 $s$，
\[
 \frac{T'}T=(1-f)+\frac f s,\qquad
 \frac T{T'}=\frac1{1-f+f/s}.
\]
arXiv 采用 $f=0.529$，预测 $1.787\times$，实测 $1.789\times$；OpenAI-3072 采用 $f=0.168$，预测 $1.175\times$，实测 $1.171\times$。其他阶段限制了收益，且分阶段剖析独立进行，因此这是解释模型。Lane 重组改变 FP32 加法顺序，相对距离误差最高为 $\approx1.6\times10^{-6}$，偶尔改变排序；其结果是速度提升，而非普遍逐位相同。

\section{留出预算质量、吞吐与回本}
\label{sec:7-5}

全池校准在十二个已测配置中均满足留出质量目标；128 查询校准更便宜，却可能频繁失效。对照采用固定 $\alpha=100$ 与 $\alpha=64$；规则定义见 \cref{ch:refinement}。

\subsection{无标签选择与带标签诊断性 oracle}

六个数据集均测试 128 和 512 probes。全池校准使用全部 500 条校准查询；采样校准按 \cref{sec:3-2} 的不相交查询池，对每种样本规模取 64 个子集。枚举在全部已测预算上检查同一规则；诊断性 oracle 用留出标签识别满足要求的预算（\cref{sec:6-4,tab:6-controls}）。全部规则变体使用 \cref{eq:6-agreement}，取 $k=10$ 和 $\epsilon=1$；标签用于评估所选预算，而非指导校准。

\subsection{全池校准作为质量优先工作点}

使用全部 500 条校准查询时，最大观测留出损失为 0.0006，十二个配置均低于 $10^{-3}$ 目标。吞吐为带标签 oracle 的 0.908--1.000，校准耗时 9.5--60.3\,ms（\cref{tab:7-budget-full}）。相对固定 100 的几何平均比为全部配置 $1.111\times$，或固定 100 也满足质量目标的十个配置 $1.193\times$。相对固定 64，校准在六个配置更快、两个持平、四个更慢。主要收益是已观察到的十二个质量目标覆盖，而不是对未来查询分布的保证。

\section{Batch 大小、调度与工作负载不均衡}
\label{sec:7-6}

在已查配置的 250 对变体／配置和 234,320 次查询比较中，调度没有引入非并列主码短名单差异或最终 ID 集合差异。并列主码的保留成员或输出顺序可以不同。性能依赖 batch 大小：相对采用 lane 精排的单 block 基线，集成调度器在 batch 为 8 时平均提升 $2.727\times$，batch 为 1,000 时为 $1.015\times$（\cref{tab:7-scheduling}）。这些平均值不表示每个配置都改善。

\section{数值检查与召回损失分析}
\label{sec:7-8}

\subsection{质量分辨率与重复执行}

降低慢 RaBitQ 调用影响后，召回率 0.97 的排序仍然保持，但接近持平的结果对数值和测量分辨率敏感。一个真实近邻命中使 Recall@10 改变
\[
 \Delta r=\frac1{nk}=
 \begin{cases}10^{-4},&n=1000,\\2\times10^{-4},&n=500.\end{cases}
\]
Stella 的 $n=499$ 步长略大；这些步长是测量分辨率，不是不确定区间。

召回率 0.97 附近，应用插值容差前，局部斜率对应每 $10^{-3}$ 召回变化 1.01--3.17\% QPS。五次构建的召回范围，Vogue 为 0.0008，arXiv 为 0.0012，OpenAI-1536 为 0.0004，OpenAI-3072 为 0.0002。这些说明局部敏感性，不能界定完整重训前沿。缓存模型下的 FP32 比较在 OpenAI 上仍有利（\cref{sec:7-precision}）；arXiv 和 LUT 接近持平的结果仍不确定。

RaBitQ 的五轮 QPS 中位范围在 Vogue 为 3.79\%，arXiv 为 3.34\%，OpenAI-1536 为 2.87\%，OpenAI-3072 为 5.25\%。这是已观察到的波动范围，不是置信区间。为检验偶发 30--60\,ms 调用的影响，将 1,000 查询速率改按 $10^6/\operatorname{median}(\text{call ms})$ 计算，而非均值调用时间。召回率 0.97 的 JHQ／RaBitQ 比值依次变为 1.063、0.995、1.118、1.100：三个有利方向与 arXiv 接近持平的结论保持。

Vogue 在身份检查与计时运行之间，召回率从 0.9642 变为 0.9644，基线自身的运行也出现此差异。另一次跨二进制身份检查中，1,000 条查询的 probe 与主码转储逐字节一致，最终召回率却不同。这些现象仍未解决；同进程内的选择检查不能解释跨进程变化（\cref{app:reproducibility}）。

\subsection{重建分数与召回损失}
\label{sec:7-recall-attribution}

重建 pilot 在已查案例中量化了较小的剩余预算相关差距，但路由与表示仍是合并局限。七个工作负载与预算配置各取 128 条查询，对全部已探测候选做 FP64 评分，相对 GPU 所选预算输出，召回提高 0--0.002344。arXiv 在 128 probes 下，$\alpha=200$ 在全部 128 条查询中返回与全 probe 重建评分相同的答案集合。预算为 100 时，召回为 0.9734375，全 probe 评分为 0.9750，差距为 0.0015625，同时存在合计 0.0250 的路由／重建损失（\cref{sec:6-2}）。

这个例子没有分离路由与重建，其他配置的比较还混入 FP64／GPU 算术差异。完整归因需要固定查询和候选集合，逐阶段测量真实近邻覆盖。\cref{tab:5-query-stages} 的阶段检查验证的是计算分数上的选择正确性，而非原始空间精确最近邻。
