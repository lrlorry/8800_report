2. 独立 CPU primary-score 全排序：接受；已有工具不能直接满足新目标。
------------------------------------------------------------------
代码核对：
* examples/demo_jhq_batch_pipeline.cu:323 起的 64 类路径检查比较 GPU
  variant 与 variant 0，不是 CPU 对全部候选的独立排序。
* scripts/test_jhq_fidelity.py:42 使用 numpy.lexsort，但随后比较 primary
  集合，并将 cutoff ties 视为允许替换；没有严格验证完整 key 的顺序。
  脚本存在不等于已有覆盖 v62/v63/v71 各分组路径的完成实验记录。
* 新发现：v69/v71 的 dump_primary_distances_kernel 仍通过 m*N+pos
  读取字节，而 jhq_gpu_index.cu:2891 起的 word repack 会把同一指针
  换为 [M/4,N] words。旧导出器不能直接假定读取的是被测 scorer 同一
  编码。它还硬编码高／低半字节 16+16，需适配其他 LUT 组数。
  此项属于 debug/test 导出路径，不是主实验 kernel 错误的直接证据。
* JHQ_DUMP_TOPCK 当前只导出 query 0；pipeline 的 .dump 则保存 probe
  和已选 top-c，不能用后者恢复未保留的全部 primary candidates。

修改：5.4 中英文明确 64 组属于 GPU 路径比较，CPU 严格参考尚待补。
待办：先适配 exporter 的布局、分组和累加顺序，再保存同一批候选的
已计算分数；G>=1 严格比较 (score,position) 全排序的成员、顺序、长度
及唯一性。G=0 用距离全预序契约，允许合法并列替换。覆盖共享界开关、
不同组数、空组／短组、候选集中与大量并列。没有宣称完成这些实验。

5. 与前一轮意见合并后的研究定位
------------------------------
GPU 一致性、同一分数的 CPU 排序、原空间 recall 是三层不同证据。
5.4/5.5 的研究主线合理：用覆盖与见证界维持选择契约，并研究实现成本；
大批量多数使用 G=0 的实际路径统计必须同时保留，不能把所有主实验
QPS 归因于多 block 或共享界。LUT 恒等式、Merge Path、radix、局部
top-c 并集原理各有先行研究；贡献落在 JHQ 表示的执行组合与可核对取舍。
原有精排公式及查询常数解释保留，未因两份审稿意见而改动公式。
