\chapter{Experimental Evaluation and Research Findings}
\label{ch:evaluation}
\chaptermark{Experimental Evaluation}

The evaluation asks whether the representation and execution choices in
JHQ-GPU improve useful ANN operating points, whether parallel execution
preserves the intended candidate selection, and whether a workload can
reduce refinement effort without an unacceptable loss of quality. These
questions require different evidence. A faster kernel does not establish a
better recall--throughput frontier, agreement with a reference result does
not establish ground-truth recall, and a resident allocation does not measure
construction peak memory. The experiments below keep these distinctions
explicit.

The main findings are conditional but consistent. Two-group Cartesian
tables and packed access improve screening; cooperative refinement reduces
residual-scoring time; and candidate-parallel scanning is especially useful
when the query batch supplies too few blocks. At batch 1,000, JHQ-GPU offers
competitive operating regions against modern GPU baselines, with both
low-recall and high-recall exceptions. Budget calibration often improves
the estimated throughput of subsequent queries, but its held-out quality
varies across workloads. The results support a system with several useful
execution regimes rather than a single configuration that dominates all
alternatives.

The E1 environment records an NVIDIA GeForce RTX 5090 with 32,607\,MiB
reported device memory, driver 595.71.05, CUDA 13.0 and cuVS 26.08.01.
The container has a 25-CPU quota; OpenMP is limited to 16 threads.
JHQ uses Release code compiled to compute\_80 PTX and JIT-compiled for the
device; the baselines use the installed native cuVS libraries. This is an
implementation comparison on one device, not an architecture-independent
algorithm ranking.

The principal cross-system timing boundary starts with FP32 queries in
host memory and ends after top-10 identifiers and distances return to host
memory and the stream synchronizes. It includes transfers, query
preprocessing and search; CAGRA int8 query quantization is inside this
boundary. Baselines reuse resource handles and output buffers. E1 uses five
timing rounds, normally 24 calls per round, with fewer calls recorded for
very slow baseline points. Its reported QPS is the median of round
throughputs, each computed from the total queries and total elapsed time.
It is not the reciprocal of the median individual-call latency. Warm-up,
index construction and any budget calibration are excluded. Device-only
baseline times are auxiliary: JHQ has no equivalent device-query API, so
mixing those times into the main ratios would change the comparison.

\subsection{Metrics and reproducibility}

All experiments use squared L2 and $k=10$. Recall is the mean fraction of
ground-truth top-10 identifiers recovered, using only the first ten
ground-truth entries even when a file stores a wider row. The refinement
factor determines $c=\max\{k,\lceil\alpha k\rceil\}$ survivors. Throughout
this chapter $\glut$ denotes Cartesian table grouping and $\gscan$ denotes
parallel scan groups; the two parameters perform different work.

The chapter's analysis script reads existing measurements without running
new GPU experiments. It verifies record counts and correctness fields,
recomputes paired ratios and matched-recall values, and writes the numeric
tables directly from those records. A companion source ledger records
SHA-256 hashes of consumed files. Its source-checkout identifier records
the audited repository snapshot; it does not imply that every historical
binary was built from that commit. Raw run headers and family-specific
reports retain the individual build provenance. This separation makes
the current figures reproducible without relabelling historical runs.\footnote{The
report repository provides \path{scripts/build_ch7.py},
\path{data/ch7/audit.json}, \path{data/ch7/matched.csv} and the source
ledger \path{data/ch7/sources.csv}. The script requires the sibling
\texttt{JHQ\_GPU} checkout containing the archived measurements.}

\section{Modern GPU ANN Recall--QPS Frontiers}
\label{sec:7-2}

\subsection{Comparison scope and frontier construction}

\Cref{fig:7-frontiers} compares JHQ-GPU with CAGRA fp32, scalar-quantized
CAGRA int8, IVF-RaBitQ, IVF-PQ and GPU brute force. CAGRA represents graph
search; PQ and RaBitQ represent compressed inverted-file alternatives
\cite{cagra,pq,ivfrabitq}. The four datasets are Vogue
($932{,}328\times768$), arXiv ($2{,}253{,}000\times768$), and the
999,000-vector OpenAI datasets at 1,536 and 3,072 dimensions. Each uses
1,000 queries and the same ground-truth file across methods.

Each method contributes its non-dominated measured operating points.
An operating point is removed if another configuration of that method
achieves at least its recall and throughput, with a strict improvement in
one. Thus a frontier combines search parameters and sometimes distinct
index configurations; it is not the trajectory of one fixed index.
JHQ contributes 27--39 points per dataset, compared with 54--264 for the
baseline families. The E1 parser finds 1,590 valid points, no failure
records and no invalid-identifier or duplicate-row flags. This count
establishes the size of the search sweep, not 1,590 independent replications.

The parameter coverage is substantive. CAGRA varies graph degree 32/64,
search width 1--8 and intermediate top-$k$ capacity 32--512. RaBitQ varies
4/8/9-bit budgets, supported search modes and probe counts up to 1,024.
PQ varies code length, lookup precision and probe count. JHQ varies both
probe count and refinement budget, extending its initial grid where recall
coverage is insufficient. The resulting comparison is conditional on
these recorded grids. A curve ending before a target recall indicates an
unmeasured operating region, not a proof that the method cannot reach it.

These curves compare achievable throughput, not equal memory consumption.
JHQ stores approximately $d/8$ primary bytes and $d$ residual bytes per
vector, plus metadata. RaBitQ at nine bits has a comparable nominal
$9d/8$ code budget, but its 4/8-bit configurations use less storage.
CAGRA int8 also stores graph edges; PQ code lengths vary; CAGRA fp32
retains FP32 vectors. Taking the envelope across these choices is useful
for deployment decisions, but cannot isolate a representation advantage
at a fixed memory budget. The memory evidence is discussed separately in
\Cref{sec:7-7}.

\subsection{Matched recall and opposing operating regions}

\Cref{tab:7-matched} quantifies the region around recall 0.97 using two

The interpolated estimator treats a measured recall within

Against CAGRA fp32, interpolated ratios at this target range from
$1.317\times$ on arXiv to $1.747\times$ on the two OpenAI datasets.
Against IVF-RaBitQ, the corresponding values are $1.059\times$,

Across targets 0.90--0.985, JHQ's interpolated advantage over CAGRA fp32
is approximately $1.10$--$2.44\times$ in the covered comparisons.
However, adding CAGRA int8 changes the low-recall interpretation: around
0.90--0.92, its lower-precision graph search can be faster than JHQ.
At higher recall, IVF-RaBitQ often regains the lead, including several
targets at 0.98 or above. On arXiv around 0.99, CAGRA fp32 is also faster
than JHQ in the recorded grid. The defensible claim is therefore that
JHQ has useful competitive regions, particularly around moderately high
recall, rather than that it dominates modern GPU ANN methods.

The two estimators can disagree substantially where the grid is sparse.
For example, at recall 0.97 the OpenAI-1536 comparison with CAGRA fp32 is
$1.747\times$ by interpolation but $2.294\times$ using qualifying measured
points. The latter includes the cost of whichever baseline point next
exceeds the threshold. It should not be presented as a directly measured
same-recall advantage of that magnitude. The companion matched table
preserves both estimators and marks targets without coverage, enabling
readers to distinguish an operating-region result from a sampling artefact.

\subsection{Interpretation and comparison limits}

JHQ combines inexpensive primary screening with selective residual
access. This provides a plausible explanation for competitive throughput
when a small fraction of scanned candidates needs refinement. The kernel
and budget ablations below test parts of that explanation directly.
The cross-system curves alone cannot assign the gain to any one component:
they also differ in routing, representation, preprocessing, index building
and software interfaces. In particular, increasing dimension across these
datasets is accompanied by changes in data distribution and dataset size.
The stronger OpenAI ratios do not constitute a controlled demonstration
that dimensionality causes JHQ's advantage.

Residual comparison limits remain after aligning the main timing boundary.
JHQ is called from C++, whereas CAGRA and PQ use Python bindings; small
host overhead differences remain even with reused resources. JHQ's output
copy targets pageable host memory, whereas baseline outputs use pinned
memory. Compilation targets differ, and unrelated host load is not fully
controlled. These effects are relevant to small margins. Five rounds
characterize repeated execution of the built indexes; they do not estimate
variation across independent index builds or independent machines.

\section{Cartesian LUT, Packed Loads and Lane Refinement}
\label{sec:7-3}

\subsection{Exact table factorization and its throughput consequence}

Cartesian factorization changes the evaluation of the represented
primary distance, rather than training a new quantizer. Splitting an
eight-bit Cartesian code into two four-bit components replaces 256 table
entries with $2\times16=32$. With FP32 entries, this changes 1,024 bytes
to 128 bytes per corresponding table, an eightfold reduction. The
mathematical score is preserved; floating-point evaluation order can still
affect the final bits. Smaller tables alone therefore do not justify
calling the complete ANN output bit-identical.

\Cref{fig:7-lut} reuses the completed table-grouping figure, checked against
the v71 raw records. It covers six datasets, probe counts 8/32/128/512,
fixed $\alpha=100$, and $\glut\in\{1,2,4,8\}$. Each arm has five timing
rounds; batch size is 1,000 except Stella's 999 queries. Two groups have
the highest median throughput in 22 of 24 cells. The exceptions are
arXiv at 128 probes, where one group is about 0.23\% faster, and
OpenAI-3072 at eight probes, where four groups are about 0.84\% faster.
These narrow differences are best treated as near ties. The newer count
is 22/24, rather than the historical ADC paper's 23/24.

\begin{figure}[tbp]
\centering
\includegraphics[width=\linewidth]{ch7/fig_lutgroups_v69.pdf}
\caption{Completed v71 Cartesian table-grouping experiment, retained from
 the existing figure set. Group counts describe $\glut$, not parallel
scan groups. Curves use median QPS normalized to the one-group arm.}
\label{fig:7-lut}

The two-group/one-group ratio ranges from $0.998$ to $1.914$.
Four and eight groups each require only 16 total entries, but differ in
the number and granularity of lookups. Their performance provides a
useful control: reducing table storage beyond the two-group design does
not necessarily improve search. Additional indexing and accumulation
work can outweigh storage savings. The measurements establish the net
trade-off; without a separate occupancy or instruction-counter experiment,
they do not identify one hardware effect as the sole cause. The maximum
reported recall spread within any four-arm cell is $10^{-4}$.

\subsection{Packed access and cooperative residual scoring}

The historical packing experiment compares byte-oriented and word-oriented
access while holding the dataset, probe count and table grouping fixed.
Across six datasets, four probe counts and $\glut\in\{1,2\}$, the 48
pairs yield throughput ratios from $1.012$ to $1.658$, with maximum recall
difference $10^{-4}$. Gains are generally smaller at eight probes and
larger at 512. Both alternatives already use a subspace-major layout;
this experiment supports packed access, not a claim that a physical
transpose alone produced the improvement. Each arm has one reported
aggregate rate, so this older evidence has weaker uncertainty information
than the five-round v71 sweep.

\Cref{fig:7-packing-refinement,tab:7-refinement} then separate wider loads
from lane cooperation in residual refinement. L0 is the original scalar
path; L1 changes the load path without distributing a candidate across
multiple lanes; L16 assigns 16 lanes to a candidate. The same process
rotates arm order across five timing rounds, with three search calls per
arm per round. For the twelve ordinary configurations, L16 improves
end-to-end throughput by $1.015$--$1.789\times$. An additional arXiv
configuration at $\alpha=200$, explicitly a high-budget control, reaches
$2.383\times$; it is not the gain range of the ordinary selected budgets.

The load-only control is bit-identical to L0 in the tested cases, yet
already improves arXiv throughput by $1.368\times$. Lane cooperation adds
a larger reduction in refinement time. On arXiv at $\alpha=100$, the
profiled refinement kernel falls from 4,277.5 to 716.8\,$\mu$s, a
$5.97\times$ gain, while total throughput improves $1.789\times$.
OpenAI-3072's refinement kernel improves $8.81\times$, but total throughput
improves $1.171\times$. This is consistent with Amdahl's law: acceleration
of a small stage cannot remove the cost of routing, screening, final
selection or transfers. It also motivates the subsequent scan and probe
experiments, which target the remaining work.

Cooperative reductions alter floating-point addition order. The tested
multi-lane variants have very small distance differences, with maximum
reported relative error about $1.6\times10^{-6}$, and occasional changes
near ranking boundaries. The evidence therefore supports numerically
close scoring with measured end-to-end gains, rather than universal
bitwise equivalence. Sanitizer checks cover the recorded refinement and
top-$k$ kernels on small query subsets; they are useful implementation
checks, not a proof for arbitrary inputs.

\section{Global Top-c, Shared Bound and Probe Correctness/Ablation}
\label{sec:7-4}

\subsection{Global primary selection before performance}

The parallel scan experiment addresses a correctness requirement that
cannot be evaluated through recall alone. Dividing a query's candidates
among blocks must preserve the global primary top-$c$; assigning each
block only $c/\gscan$ survivors can discard a globally competitive
candidate from a disproportionately productive group. JHQ's v62 path
instead retains up to $c$ candidates in every group and merges the local
lists. Selection uses the complete key $(\primarydist,\mathrm{position})$,
where position breaks primary-distance ties deterministically.

The local retention rule has a direct justification. A candidate in the
global top-$c$ has fewer than $c$ preceding keys in the entire candidate
set, and hence fewer than $c$ in its own group. It must therefore appear
in that group's local top-$c$. Taking the top-$c$ of the union, with the
same total order, recovers the global top-$c$. This statement concerns
primary scores over the visited candidates. It does not make IVF routing
exact, turn primary scores into raw distances, or make the final ANN
answer an exact nearest-neighbour result.

The v62 checker covers four workloads, batches 8/32/256/1,000 and group
counts 1/2/4/8, giving 64 comparisons. It reports no non-tie primary
selection differences from the original one-block path, zero change in
compared primary distances, and bit-identical final top-10 identifiers
and distances for every used query. The original path sorts on distance
alone, so its primary cutoff can select a different member of a tie;
these differences do not violate the new complete-key specification.
They also did not change final outputs in this particular experiment.

The number of used queries deserves attention. The harness submits only
complete batches: out of a 1,000-query pool it uses 992 queries for batch
32 and 768 for batch 256, whereas batch 8 and batch 1,000 use all 1,000.
Correctness counts and timing populations therefore depend on the batch
regime. They cannot be described as the identical 1,000-query test in
every row. Recorded memcheck, racecheck and synccheck runs provide
additional checks on smaller subsets and on the named scan/merge kernels.

\subsection{Shared bounds preserve the selection target}

Keeping a full local top-$c$ is safe but potentially expensive. In v63,
groups of one query publish a shared bound using the same complete key.
Once any group has established $c$ keys no greater than a bound, a
candidate worse than that bound cannot enter the global top-$c$. A
stale, looser bound can cause extra admissions, but cannot legitimately
exclude a better candidate. This requires that a published bound be
backed by enough valid candidates and that atomic updates preserve the
complete-key ordering; an approximate distance threshold alone would
not establish the same tie behaviour.

The implementation still computes every scanned candidate's complete
primary score before deciding admission. The bound reduces selection,
compaction, sorting and downstream merging work; it does not prune primary
distance evaluation or avoid reading every rejected primary code. This
scope matters when interpreting an apparent scan-stage speedup. A faster
scan stage need not mean fewer evaluated distances.

The dedicated v63 checks compare shared-bound groups 2/4/8 with their
independent-bound counterparts across the four workloads and four batch
sizes. All 48 comparisons report identical primary top-$c$ and final
outputs. Five-round paired throughput measurements range from about
$0.994$ to $1.562\times$ relative to independent bounds. Thus sharing
substantially helps some expensive cases but is not uniformly faster.
On arXiv at $\alpha=200$, batch 1,000 and eight groups, the profiled
merge cost falls from approximately 2,629 to 471\,$\mu$s. The result
supports reducing excess intermediate work rather than claiming that
more scan groups are always beneficial.

A rejected alternative was to allocate smaller static local quotas.
The campaign's distribution measurements place 46--81\% of the global
survivors in the first candidate group for the pilot workloads. Equal
quotas would frequently require a correctness fallback, and calibrated
unequal quotas still leave the dominant group on the critical path.
These observations motivated the exact shared bound. They are pilot
measurements of those workloads, not a theorem that every possible quota
policy is inferior.

\subsection{Exact probe selection and the limits of pipeline identity}

Once screening becomes faster, IVF probe selection becomes a larger
fraction of small-batch time. The v69 probe primitive changes how the
smallest centroid scores are selected while retaining FP32 scoring.
Its synthetic checker covers 1,792 cases and reports zero failures.
Checks of the real arXiv, Vogue and OpenAI-3072 workloads find identical
probe identifiers and identical primary top-$c$ positions and distances
for all 1,000 queries. These are more specific observations than a single
unchanged recall number: they test the routing and screening outputs
directly.

\section{Held-out Budget Quality, Throughput and Payback}
\label{sec:7-5}

\subsection{Unlabelled selection and a labelled diagnostic oracle}

The budget experiment fixes one trained index per dataset--probe cell and
compares fixed budgets, sampled calibration, full-pool calibration,
same-sample enumeration and an offline oracle. The six datasets are tested
at 128 and 512 probes. Even-indexed queries form a calibration pool of
500; odd-indexed queries form a disjoint held-out pool of 500, except
Stella, which has 499. Samples of $S\in\{32,64,128\}$ are drawn from the
calibration pool without replacement within each draw, using a fixed
random seed, with 64 draws per size. Repeated draws reuse a fixed finite
query pool; they are not 64 independent samples of future workload drift.

The descending grid is $A=(200,100,64,32,16,8,4,2)$. Calibration compares
candidate top-10 identifier sets with the $\alpha_{\max}=200$ reference.
For sample $\mathcal Q_S$, the acceptance statistic is
\begin{equation}
 D_S(\alpha)=\sum_{q\in\mathcal Q_S}
 \left(10-|\mathcal R_\alpha(q)\cap\mathcal R_{200}(q)|\right),
 \qquad D_S(\alpha)\leq 1.
 \label{eq:7-agreement}
\end{equation}
The allowance is one disagreeing result slot over the entire sample,
not one per query and not a ground-truth recall tolerance. No labels
are supplied to the deployed rule. The reference is itself approximate,
so perfect agreement can reproduce its errors.

The offline oracle has a different role. After observing held-out recall
for all eight fixed budgets, it selects the fastest measured arm within
$10^{-3}$ of the best measured held-out recall. This is a diagnostic
benchmark, not an implementable label-free decision. Likewise, ``full
pool'' means applying the same calibration search to all 500 calibration
queries; it does not mean enumerating every budget with held-out labels.
The distinctions prevent an apparent oracle match from being mistaken
for a quality guarantee.

\subsection{Budget quality and sampling risk}

\Cref{tab:7-budget-quality} reports the $S=128$ result. The median selected
budget matches the oracle budget in ten of twelve cells; it differs on
arXiv at 128 probes and OpenAI-3072 at 512. The selected budgets span
4--200, indicating substantial workload dependence. However, a median
budget and a mean recall describe different aspects of the draw
population. They need not correspond to the performance of one arm.
In addition, mean recall in the table is reconstructed from the printed
best recall minus printed mean loss, so its four-decimal precision is
approximate.

The important counterexample is arXiv. At 128 probes, 40/64 draws lose
more than $10^{-3}$ recall even though mean loss is only 0.0009; at
512 probes, 32/64 draws cross the threshold. BGE at 512 probes has
24/64 threshold crossings and a 95th-percentile loss of 0.0014. Stella
has fewer crossings but a 95th-percentile loss of 0.0030 at both probe
depths. Thus mean quality, violation frequency and tail magnitude must
be read together. OpenAI-3072 has no observed threshold crossings in
these draws, which supports a favourable result on this pool, not a
zero-risk statement about unseen queries.

The percentile convention also matters for this small sample of draws.
The harness reports the sorted loss at zero-based index
$\lfloor0.95(64-1)\rfloor=59$, rather than interpolating between order
statistics. Consequently, four nonzero tail losses can coexist with a
printed $L_{95}=0$, as on OpenAI-1536. The table preserves this logged
statistic and the exact crossing count; zero in that column does not
mean every draw has zero loss.

Same-sample enumeration agrees with bisection in all 2,304 draws

held-out failures. Nor does empirical agreement establish universal
monotonicity: the deployed final selector retains a bounded number of
thread-local candidates, so the exact-selection assumptions needed for
a general monotonicity argument are not assured.

calibration is not identical to the oracle either: on Vogue it selects
100 at both probe depths while the oracle selects 64. Agreement-based
selection and fastest quality-constrained selection solve different
problems, even with a larger calibration sample.

Unlike E1, this family times each fixed arm with a warm-up and three
search calls. The rule's reported QPS is then the arithmetic mean of
the already measured QPS values of its 64 selected arms. It is not a
new timing of a service repeatedly calibrating and executing the policy.
At $S=128$, this selected-arm estimate improves over fixed $\alpha=100$
in ten cells, by $1.028$--$1.691\times$. On arXiv the ratios are 0.908
and 0.917: mean recall improves, but throughput falls. Those cells have
no throughput payback.

The calculation is optimistic. In general,

workload can benefit; a short job or a changing query population may
not. The present experiment measures neither drift detection nor a
production recalibration schedule.

\section{Batch Regimes, G Scheduling and Workload Skew}
\label{sec:7-6}

\subsection{Parallelism versus repeated selection work}

The scan experiments reveal two execution regimes. With one block per
query, batch 8 exposes only eight blocks on a 170-SM device. Candidate
partitioning increases the available block parallelism. In the v62
experiment, eight groups improve end-to-end throughput by
$2.06$--$2.76\times$ at batch 8. Profiling supports a stage-level
explanation: arXiv's scan falls from about 849 to 216\,$\mu$s, Vogue's
from 1,059 to 246\,$\mu$s, and OpenAI-3072's from 728 to 155\,$\mu$s.
The additional merges cost approximately 16.7, 9.1 and 3.7\,$\mu$s,
respectively. The net reduction is large even after paying for merging.

At batch 1,000 there are already enough independent queries to expose
many blocks. Additional groups repeat table staging, local-buffer
admission and sorting, and produce extra merge traffic. The unshared
v62 path can fall to about $0.46\times$ its one-block baseline on
arXiv at $\alpha=200$. This opposing result is central to the design:
parallel decomposition solves insufficient concurrency, but incurs work
that can dominate once concurrency is adequate. Shared bounds reduce
that extra work but do not eliminate the regime change.

\subsection{A fixed rule evaluated on further configurations}

The integrated v65 scheduler chooses a scan-group count using batch size,
block size and a workload-skew estimate. Its fill rule relates the
potential resident threads to a fixed 0.6 fraction of the device's
thread capacity. Its skew rule requires at least four groups when the
coefficient of variation of candidates per query is at least 0.3. The
larger suggested group count is used, with the one-group case mapped to
the original one-block scan. The skew statistic is estimated once from
512 database vectors used as pseudoqueries, not from ground-truth labels
or the evaluated query pool. The constants were chosen on four workload
configurations before the additional configurations were measured.

Candidate-count CV does not capture every cost of list traversal,
selection or merging. This failure identifies a limitation of the chosen
feature rather than evidence that execution scheduling is unnecessary.

Vogue illustrates why batch size alone is insufficient. Its measured
candidate-count CV is about 0.51, compared with roughly 0.08--0.11 for
the original other workloads, and its heaviest query has around 2.2 times
the mean candidate count. Splitting candidates can shorten a slow query
that would otherwise determine completion of a synchronous batch. This
explains why Vogue can still benefit from multiple groups at larger
batches, although the CV observations are workload evidence rather than
a general causal isolation of skew.

Finally, correctness is checked independently of timing. Across 250
variant/configuration comparisons and 234,320 query comparisons, the
integrated campaign reports no non-tie primary-selection differences and
no different final identifier sets. Final order can differ at ties;
the entire campaign should not be described as universally bit-identical.
The throughput results concern sequential, synchronous submissions and
do not establish tail latency under an open-loop arrival process.

\Cref{fig:7-memory} retains the completed memory-component figure. Its

Residual codes dominate the large datasets: approximately 80.7\% of

The corresponding raw FP32 vector arrays alone would require 38.50
and 67.81\,GiB. JHQ therefore enables the tested resident search on one

query-specific table storage, not the database's residual-code precision.

Workspace also matters. The reported list-group scratch is approximately
93.8\,MiB in these $\alpha=100$ measurements, reserved for a batch
capacity of 1,024 and up to eight groups even when the selected execution
uses the one-block path. A smaller actual group count therefore does
not imply that the allocation shrank proportionally. Conversely, these
resident samples do not capture temporary construction peaks. The
baseline harness also initializes some search memory pools after its
index-memory measurement, so an after-build index delta cannot be used
as a complete peak process-memory budget across methods.

BGE contains 10,091,524 vectors and Stella 17,776,615, both with

the corpus; its result therefore characterizes that benchmark rather
than an independently collected external-query distribution.

successful CAGRA int8 and IVF-PQ measurements. Full-precision CAGRA,

\section{Numerical Robustness, Anomalies and Recall Attribution}
\label{sec:7-8}

\subsection{Quality resolution and repeated execution}

With $k=10$ and 1,000 queries, one recovered neighbour changes aggregate
Recall@10 by $10^{-4}$; with 500 held-out queries the resolution is
$2\times10^{-4}$. Stella's 499-query split has a slightly coarser
resolution. This discretization is not an uncertainty interval, but it
helps interpret the small differences reported above. A fourth-decimal
change may represent only one or two result slots, while a small mean
loss can still hide several queries with substantially changed answers.

Repeated timing calls must also be separated from repeated index builds.
The E1 parser records 369 baseline operating points with a false
identifier-determinism flag: 170 RaBitQ, 80 IVF-PQ, 68 CAGRA int8,
50 CAGRA fp32 and one brute-force point. This flag can include result
order changes at ties; it does not by itself imply changed identifier
sets or invalid output. No such point is discarded solely for that
flag. The raw logs retain first/last recall and set/order diagnostics.
JHQ does not populate this same baseline flag, so its absence cannot
be counted as a uniform cross-method determinism test.

The five-round throughput summaries retain variability within a fixed
build. Minima and maxima are descriptive ranges, not confidence
intervals, and they do not account for training variation. Small
throughput margins such as the two LUT near ties, or the arXiv--RaBitQ
comparison at recall 0.97, consequently receive limited interpretive
weight. Larger repeated gains with a matching stage-time reduction
provide stronger evidence for an execution improvement than a small
frontier displacement alone.

\subsection{Exactness is attached to a particular stage}

Several distinct claims must remain separate. Cartesian factorization
preserves the represented score algebraically. Packed loads preserve the
logical code values. Complete-key local retention and merging recover
the exact primary top-$c$ of the visited candidates. The shared bound
preserves that selection target. The FP32 probe primitive passes its
synthetic and real-input equivalence checks. None of these establishes
exact nearest-neighbour answers in the original vector space.

Lane reductions can alter rounding; primary cutoff ties can change
which survivor is refined; approximate final selection can change a
boundary result. The archived Vogue cross-version discrepancy shows why
a pipeline-wide identity claim requires its own check. Similarly, the
FP16 routing experiment demonstrates that an almost unchanged mean
recall is insufficient evidence of exact probe equivalence. The main
correctness conclusions are therefore stated at the stage and input
coverage actually tested.

Recall loss can enter at routing, primary screening, residual scoring
or final selection. Increasing probes expands routing coverage;
increasing $\alpha$ gives more primary survivors access to residual
scoring; neither restores information lost by every later approximate
stage. The budget sweep directly measures the consequence of changing
survivor count while holding the index and probe configuration fixed.
It does not decompose every missing neighbour into a unique cause.
A complete per-query attribution would require ground-truth coverage
checks after routing, after primary retention and after refinement,
with an exact final-selection reference on the same candidate set.
That full attribution is not established by the experiments used here,
and no percentages are assigned to unmeasured sources of loss.

\subsection{Scope of the research findings}

Taken together, the evidence supports representation-aware execution,
exact parallel primary selection and workload-specific refinement
budgets as useful components of GPU JHQ. It also identifies their
boundaries: more parallel groups can increase work, smaller tables can
require more lookups, sampled agreement can generalize poorly, and
compressed residency retains a substantial residual-storage cost.
These are informative negative results because they constrain the
mechanisms offered to explain the positive results.

The claims apply to the exported squared-L2 workloads, top-10 search,
the recorded query pools and the tested RTX 5090 environment. They do
not establish behaviour for another GPU, a different $k$, changing
query distributions, online updates or concurrent service arrivals.
Within that scope, the strongest evidence combines a controlled change,
explicit correctness checks, a repeated end-to-end gain and a measured
reduction in the targeted stage. The following discussion can therefore
build on verified operating regions and mechanisms without treating
unmeasured deployment properties as established results.
